# 进度、邮箱与恢复

显示报价、付款码图片、文本码、可点击链接和会话 UUID 后，让本次工作停在「等待付款」这一步。先用用户可见的消息输出付款信息，然后发起可等待的宿主工具调用。不能把二维码藏在一个要等到付款才返回的工具结果里。此时只监听已验证的回调或用原会话凭据查询 `/status`（按 `nextPollAfterMs`，付款前通常约 5 秒）；未创建 runId 时使用会话状态接口。避免逐次向用户重复输出「待付」。单次工具调用超时则接续同一会话，网络断开后重连；用户明确取消或订单已关闭时退出本单等待。宿主确实无法持续等待时如实说明恢复方式。

收到到账回执或账户启动成功后，在用户对话展示预计评审用时；收到实际阶段事件才说开始预处理或评审。遇 `paid_pending_start` 继续查原任务。等待和后续跟进全程不打开原件自行评审。可选询问一次：

> 要留下联系邮箱吗？报告可交付时自动发送，也可以跳过，稍后直接选择下载位置。

用户填写后 `PATCH /review-sessions/{id}/contact`，请求 `{"email":"用户明确提供的邮箱"}`；跳过则传 `{"email":null}`。不得猜测邮箱或替用户填写其他人的地址。等待回答不阻塞服务器任务，未收到回答时继续查看进度，不因邮箱问题重跑或停掉分析。

`GET /status?afterSequence=<游标>`返回阶段、价格、费用状态和分页事件。处理每批后保存游标；`hasMoreEvents=true`时继续读取，直到追平，不能直接跳到尚未读取的序号。

**实际建立跟进通道。** 优先让宿主后台监听原会话的 SSE，已有可验证的 HTTPS 接收地址时使用[签名回调](../api/callback.md)唤醒宿主。只支持轮询时每 60 秒查询一次简报。使用能唤醒对话或返回工具结果的宿主任务，先确认监听或定时查询确实建立。宿主只能前台等待时保持这一轮会话；不能持续运行时，把会话编号和「继续查询本单进度」恢复指令交给用户。

有 runId 后访问 `/events?afterSequence=<已消费游标>`。SSE 连接正常结束也要续接；流中断、回调跳号或连续 5 分钟静默时，用简报补查。回调序号与日志游标分别保存。

REST 简报为 `GET /status?view=brief&afterSequence=<游标>&runId=<原运行编号>`；MCP 用 `get_review_progress(task_id, view="brief", after_sequence=游标, run_id=原运行编号)`，第一次可省略运行编号。保存响应的 runId 和 lastSequence，hasMoreEvents 为真时立即追平。新 runId 的游标从零开始。updates 合并了同一文件的逐页回执，overallProcessedUnits 和 overallTotalUnits 是整个批次的实测值。

**要把进展写进用户看得见的对话。** 预处理、OCR、正式评审、汇总复核、报告生成和报告可领取分别提醒一次。同一阶段距上次播报约 5 分钟即主动发一条，采用最新的文件、页数或核验事项。核实没有新活动时写最近真实业务时间 lastActivityAt；断网时说明上次成功同步时间并重连。按任务持久保存已播报阶段、游标和上次播报时刻，回调、SSE、轮询或重启不能重复播报。已补齐多个历史阶段时可合成一条时间线。领取、失败或取消后结束常规跟进。

游客从第一次展示本单起，每条阶段通知、五分钟小结和最终通知都附上 Markdown 链接「查看本单详细进度」。链接文字不附到期时刻或其他括注。完整使用服务端返回的 progressUrl（包括 # 后的只读凭证），progressUrlExpiresAt 从第一次签发起固定 24 小时。过期后只用原 Agent 继续跟进。不要把 accessKey、API Key、邮件地址或付款链接拼入进度网址。账户任务照常跟进。

访客取码前只展示材料与处理进度；第一次展示价格和付款、到账说明必须与实际二维码在同一条消息。付款前不得索取、还原、猜测或转述报告草稿、问题结论、原文证据或下载地址。

`report_verified`表示完整问题报告及必要核验记录已生成并验证、执行资源已释放。按[付款参考](../payments/settlement.md)核对原账单；费用结清后交付。

Agent重启后读取本机恢复记录，查询原任务继续。失败、取消或超时不收费；不要把系统故障改写成业务风险或编造一份报告。
